# Changelog

Todos los cambios relevantes de este proyecto se documentan en este archivo.

El formato sigue [Keep a Changelog](https://keepachangelog.com/es-ES/1.1.0/) y el proyecto usa [Versionado Semantico](https://semver.org/lang/es/).

## [Unreleased]

### Added

- Preflight de colision antes de `install`/`update`: detecta que archivos no protegidos por el sidecar de hashes ya existen en el destino y pide confirmacion interactiva (`y/N`, default `N`) antes de sobrescribirlos. En modo no interactivo (CI/pipe) aborta con codigo 1 listando las colisiones a stderr, y el flag `--force` salta la confirmacion. Los archivos ya cubiertos por la proteccion de ediciones locales quedan fuera del preflight
- Deteccion de instalacion interrumpida: un lockfile (`.sdd-install-in-progress`) se escribe antes de copiar y se retira al terminar por cualquier via de salida, incluida una excepcion inesperada. Una ejecucion de `install`/`update` que encuentra el lockfile de una ejecucion anterior aborta con codigo de salida 1 sin copiar nada, nombrando la fecha y el backend de esa ejecucion previa; un lockfile con JSON invalido aborta igual, con un mensaje generico
- Aviso del coste de `claude-opus-4-8` como modelo de sesion por defecto tras `install --backend claude`/`all`, con la via para cambiarlo (`/model` o editando `settings.json`), tanto en el README como al terminar la instalacion
- Aviso en el README sobre el riesgo de sobrescritura al instalar sobre un proyecto existente (deteccion de colision, comportamiento en TTY vs CI, y los archivos protegidos que quedan fuera de esa deteccion), con `--dry-run` documentado como primer paso recomendado antes de instalar sobre un proyecto existente
- Nota en el README explicando por que el framework no ofrece una via nativa de plugin de Claude Code: un plugin se copia al cache de Claude Code, no a tu proyecto, asi que no puede entregar `CLAUDE.md` como contexto del proyecto ni escribir `.claude/agents/`, `.claude/commands/`, `.claude/skills/` ni `hooks/` en tu repositorio, que es justo lo que hace `npx ... install --backend claude`
- Tests de contrato para instalacion secuencial de varios backends en el mismo proyecto (`claude` seguido de `gemini` o `codex`): verifican que los archivos propios de cada backend se preservan y que los archivos comunes se refrescan de forma identica a una instalacion limpia
- **Modo concurrente a peticion en `/implementar-spec` (`--parallel`).** Sin el flag el comportamiento no cambia: cada task se implementa, se revisa y se commitea antes de empezar la siguiente. Con el flag, las tasks de un mismo nivel de dependencias arrancan a la vez; los niveles se siguen recorriendo en orden. Las puertas de calidad son identicas en los dos modos: la suite del proyecto se ejecuta de verdad por task y cuenta su codigo de salida real, el diff de cada task pasa por revision adversarial antes del commit y la ultima task cierra con la comprobacion de convergencia con la spec. Una task fallida no cancela a sus hermanas. Lo que el framework NO hace en este modo: no reparte los archivos entre tasks, no detecta que dos tasks del mismo nivel escriban el mismo archivo y no aisla el arbol de trabajo, asi que el descarte de una task fallida se lleva por delante los cambios sin commitear de sus hermanas. Pedir `--parallel` solo con tasks que tocan archivos disjuntos es responsabilidad de quien invoca; el README documenta los dos modos lado a lado con la frontera de responsabilidad. Solo el backend de Claude Code tiene motor de workflows: en los demas, el orquestador implementa las tasks en orden

### Changed

- **Las diez skills que Codex y Antigravity mantenian a mano pasan a generarse desde su comando.** `.agents/skills/{asesor,auditar,estado,implementar,implementar-spec,inicio,planificar,revision,spec,tareas}/SKILL.md` eran copias sin lazo mecanico con su origen: una regla anadida al comando de `.claude/commands/` llegaba a Claude Code y a Gemini CLI, y a esos dos backends solo si alguien la portaba a mano en la misma PR. Ahora salen del mismo comando con el transform `command-to-skill`, y el gate de deriva (`npm run check-drift`) las verifica como a cualquier otra salida generada. Lo propio del formato de skill (el frontmatter de activacion, y el texto que solo tiene sentido ahi) se declara en `docs-src/skills/<nombre>.md`; `planificar` e `implementar-spec` declaran ademas `source-body: omit` y aportan su procedimiento completo, porque su comando delega en el motor de workflows que solo tiene Claude Code, que es la misma excepcion que ya tenian esos dos comandos para Gemini
- Un bloque `<!-- solo-claude -->` … `<!-- /solo-claude -->` dentro de un comando marca el texto que solo vale en el backend de Claude Code y no llega a ninguna otra superficie generada. Es la via para que una instruccion viva en el comando canonico sin propagarse; sin marcador, todo el cuerpo viaja
- **El trabajo de una task a la vez pasa de regla del framework a modo por defecto.** Los documentos de contexto de los cuatro backends, las plantillas de planificacion y el README presentaban "una task tras otra" como el unico modo posible, y algunas superficies llegaban a descartar la ejecucion concurrente. Ahora todas describen lo mismo que hace el producto: implementar una task tras otra es el comportamiento por defecto y no necesita ningun flag; la ejecucion concurrente existe, se pide de forma explicita y la decide quien invoca. Las puertas de calidad no dependen del modo elegido
- **El framework deja de declarar un modo de ejecucion por defecto: ni lo prohibe, ni lo prescribe.** El cambio anterior corrigio la prohibicion pero la sustituyo por la prescripcion contraria (un "por defecto" declarado como comportamiento del producto), lo que dejaba dos afirmaciones incompatibles conviviendo en el mismo repositorio: la plantilla de roadmap ya delegaba la decision en quien implementa el plan, mientras el nucleo compartido, sus tres fragmentos de backend, el comando `/implementar-spec`, las plantillas distribuidas (`core_templates/`, `dev_templates/`), los manifiestos (`package.json`, `gemini-extension.json`) y el ejemplo de dogfood seguian fijandola como regla. Ahora ninguna superficie nucleo, plantilla o manifiesto narra el par defecto/peticion como comportamiento del framework: el orden de dependencias sigue siendo un hecho estructural del plan, y si se ejecuta en secuencia o en paralelo lo decide quien implementa. La capacidad tecnica (el flag `--parallel` de `/implementar-spec` y el computo de niveles de dependencia) no cambia. Los dos tests que exigian la doctrina (`tests/backend-parity-content.test.js`, `tests/compile.test.js`) dejan de exigirla sin perder la red que impide reintroducir la prohibicion contraria (`negacionCategorica` sobre el README); `tests/vocabulario-concurrencia.test.js` deja de exigir que los manifiestos califiquen el modo lineal de "por defecto" y su comentario de contrato deja de certificar esa redaccion como "la descripcion correcta del producto", conservando intacto su barrido anti-prohibicion. Se corrigen ademas, en la misma revision: el wiring de Antigravity, ausente de la seccion de hooks del README pese a estar cableado (con un canario nuevo que impide que vuelva a faltar); la promesa de que las reglas de Cursor replican el flujo SDD (ninguna de las 43 lo hace); un modo `enforce` de `sdd-turn-budget` que podia bloquear su propio checkpoint cuando el commit pendiente incluia un archivo nuevo; el corazon del gate de tests (`evaluarGateTests`/`descubrirComandoTest`) sin ningun test directo pese a ser la garantia central de que el gate ejecuta el comando real; y el modelo de sesion anunciado por el instalador, que citaba `claude-opus-4-8` de memoria en vez de leerlo de `.claude/settings.json`
- **Carpetas del backend Gemini namespaced bajo `.gemini/`.** `agents/`, `commands/` y `skills/` del backend Gemini pasan de instalarse como carpetas sueltas en la raiz del proyecto a `.gemini/agents/`, `.gemini/commands/` y `.gemini/skills/`, alineado con la convencion propia de Gemini CLI para comandos y subagentes de proyecto, y evitando colisionar con carpetas homonimas de otros frameworks. Como contrapartida, la via nativa `gemini extensions install` ya no puede empaquetar comandos/skills/agentes desde la raiz (solo el archivo de contexto); el README documenta el tradeoff. `install`/`update` avisan (sin bloquear) si detectan un proyecto con el layout antiguo sin namespacing
- **La proteccion de ediciones locales de `update` deja de limitarse a 6 rutas fijas.** Antes solo protegia `hooks/config.json`, `.claude/settings.json`, `CLAUDE.md`, `GEMINI.md`, `AGENTS.md` y `.gitignore`; ahora protege por hash cualquier archivo que copia el framework (un hook individual, `CHANGELOG.md`, etc.), comparando contra el sidecar de hashes antes de sobrescribir y reportando los que se saltan. `--reset-protected` sigue funcionando para cualquier archivo; `install` mantiene su alcance mas estrecho (esas colisiones pasan por el preflight de confirmacion/`--force`). Un sidecar de hashes corrupto o a medio escribir ahora avisa por stderr y trata los archivos como sin hash previo, en vez de fallar en silencio
- `/estado` dejaba de contar con fiabilidad las tasks "completadas"/"en progreso": ningun paso del flujo real actualiza el campo `Estado` de un task doc tras crearlo, asi que ese contador era sistematicamente incorrecto; y la tabla mostraba una columna "Independiente" que ninguna plantilla de tasks llega a definir. El comando ya no promete esos dos datos
- El documento de contexto del backend Antigravity (`AGENTS.md`) mantenia a mano una copia de las secciones comunes a los demas backends, sin ningun lazo mecanico con su origen. Ahora adopta el mismo nucleo compartido que ya usan `CLAUDE.md` y `GEMINI.md`, para que las tres superficies dejen de poder divergir en silencio
- La configuracion del backend Codex y la guia de contribucion afirmaban que un flujo de integracion continua reforzaba la validacion del repositorio; este repositorio no tiene ningun flujo de CI configurado. Se retira esa promesa de la documentacion; la comprobacion sigue disponible como paso manual, explicado en la guia de contribucion
- Los agentes de rol de solo lectura (asesor, revisor) ya declaraban su lista blanca de herramientas en tres de los cuatro backends, aplicada por la propia plataforma antes de que el modelo actue. En el backend que faltaba esa restriccion solo vivia como texto en el prompt, sin ningun mecanismo que la hiciera cumplir; ahora la aplica la plataforma tambien ahi, igual que en los demas

### Removed

- `.claude-plugin/plugin.json`: el manifiesto de plugin nativo de Claude Code sale del repositorio. Nunca fue una via de instalacion viable (un plugin se copia al cache de Claude Code, no al proyecto) y mantenerlo solo servia para sugerir una via que no existe. La instalacion sigue siendo `npx ... install --backend claude`

### Fixed

- `/estado` no sabia reportar las tasks de convergencia en Codex ni en Antigravity: la clasificacion de `NNN_convergencia_<spec>.md` y la linea "Tasks de convergencia pendientes" estaban en el comando de Claude Code y en el de Gemini CLI, pero no en la skill que leen los otros dos backends, que si generan esas tasks al cerrar una spec. Al generarse la skill desde el comando, los cuatro backends reportan lo mismo
- La skill de implementacion de una spec completa (Codex y Antigravity) solo contemplaba dos veredictos de convergencia (`CONVERGIDA` y `DIVERGE`) y no decia que hacer cuando una task quedaba FALLIDA o BLOQUEADA. Se anade el tercer veredicto, `OMITIDA`, ya presente en el comando de Claude Code, con la via de salida: resolver esas tasks y volver a lanzar la implementacion
- El aviso sobre el gate de revision aparecia en los comandos `revision` e `implementar` del backend de Gemini CLI, donde ese hook no se cablea y por tanto no hay forma legitima de satisfacerlo — justo lo contrario de lo que declaran `GEMINI.md` y la tabla de mapeo de hooks. El aviso queda marcado como exclusivo de Claude Code y ya no viaja a los demas backends
- `/estado` sugeria derivar tasks de cualquier spec sin tasks, incluidas las que siguen en BORRADOR, cuando solo se derivan tasks de specs APROBADAS. Ahora la sugerencia se limita a las specs aprobadas en los cuatro backends
- `install` ya no sobrescribe el `package.json` del proyecto destino con los metadatos del framework (nombre, version, dependencias y scripts). Se excluye del manifiesto de copia; en su lugar, `install`/`update` fusionan solo `scripts.test`, creando un `package.json` minimo si no existe o anadiendo la entrada solo si el proyecto no define ya su propio script de test
- El `.gitignore` del framework llegaba vacio a los proyectos instalados via `npx ... install`: sin `.npmignore`, npm usaba `.gitignore` como reglas de empaquetado en vez de distribuirlo como archivo. Se anade `.npmignore` con las exclusiones de desarrollo y una regla de negacion explicita para forzar la inclusion de `.gitignore`, que `npm-packlist` excluye por defecto de cualquier paquete
- `deduplicarRutas()` reordenaba las rutas del manifiesto de copia por longitud de string para detectar solapamiento de subcarpetas, y devolvia esa lista ya reordenada en vez del orden original del manifiesto, alterando la prioridad de copia prevista. El orden por longitud se usa ahora solo internamente para detectar cobertura; el resultado se devuelve en el orden original del manifiesto
- Un fallo al copiar una sola ruta del manifiesto (por ejemplo `EACCES` en una subcarpeta) abortaba toda la copia con una excepcion sin capturar, dejando el destino en un estado parcial sin ningun reporte de lo que ya se habia escrito. Cada ruta se copia ahora en su propio `try`/`catch`: un fallo no aborta el resto, las rutas fallidas se reportan por stderr, el sidecar de hashes solo registra las rutas copiadas con exito, y `install`/`update` terminan con codigo de salida distinto de cero si hubo al menos un fallo
- `update` copiaba el framework y reportaba exito incluso sobre un directorio que nunca tuvo una instalacion previa, sin crear `ai_docs/core/`, `ai_docs/tasks/` ni `ai_docs/refs/` (esas carpetas solo las crea `install`). Ahora `update` comprueba que existe una instalacion previa (sidecar de hashes o el marcador `<!-- sdd-framework: X.Y.Z -->`) antes de copiar, y aborta con un mensaje claro recomendando `install` si no la encuentra
- `npm test` fallaba de forma determinista justo despues de cualquier instalacion nueva: un test leia `README.md` con `fs.readFileSync`, pero ese archivo nunca se copia al proyecto destino, y el flujo de instalacion instruye correr `npm test` inmediatamente despues de instalar. El test ahora comprueba la existencia de `README.md` antes de leerlo y se salta si esta ausente
- `GEMINI.md` afirmaba que el modelo lo decide la configuracion de la CLI, pero los cuatro agentes del backend Gemini fijan `model: gemini-2.5-pro` en su frontmatter. Se corrige la seccion "Modelo por defecto" para describir que el modelo esta fijado por agente (los cuatro comparten el mismo, a diferencia del backend Claude, que lo diferencia por rol) y que cambiarlo requiere editar el campo `model:` de cada archivo de agente
- Nota de `scripts/hook-event-mapping.json` que atribuia a `.codex/rules/` una compensacion inexistente por la ausencia de un hook de lectura-antes-de-editar en Codex; ese archivo solo prohibe `git commit`/`push --no-verify` y no tiene ninguna regla relacionada con lectura previa. Se reescribe la nota con el motivo tecnico real: no existe un evento de lectura equivalente para alimentar el tracker
- `GEMINI.md` era el unico de los tres documentos de contexto que describia `sdd-commit-guard.js` como puramente informativo; el hook en realidad deniega `git commit`/`push --no-verify` y solo avisa sobre problemas de formato del mensaje. Se corrige la fila de la tabla de hooks para igualar lo ya documentado en los otros backends
- La skill compartida de planificacion (backends Codex y Antigravity) imponia como lanzar la revision de cada tarea, contradiciendo lo que hace el mismo paso en Claude Code, que las lanza a la vez. Como ninguna revision necesita el resultado de otra, el paso deja de imponer un modo: declara que son independientes y que el orden no cambia ningun veredicto, y aclara que solo la auditoria cruzada final necesita todas las revisiones terminadas
- `/inicio` (bootstrap de `ai_docs/core/`) faltaba en las tablas de comandos/skills de `CLAUDE.md`, `GEMINI.md` y `AGENTS.md` que los agentes cargan cada sesion, pese a que el README ya lo recomienda como primer paso
- Las plantillas de auditoria y revision usaban veredictos separados por espacios (`NECESITA AJUSTES`, ...) mientras el schema JSON del flujo de planificacion exige valores separados por guion bajo; una invocacion aislada de esas plantillas (fuera del flujo automatizado) emitia el formato incompatible. Se unifican los veredictos literales de ambas plantillas al formato con guion bajo
- La regla "cada tarea genera al menos un commit" no reflejaba que una tarea que no pasa la revision adversarial se descarta sin commit; se reformula en los cuatro backends y en las plantillas de derivacion de tareas y commit a "cada tarea aprobada genera al menos un commit; las tareas fallidas (revision adversarial no superada) se descartan sin commit"
- `AGENTS.md` afirmaba que los `.toml` de `commands/` seguian siendo validos para el backend Antigravity, pero su manifiesto de instalacion solo copia `.agents/` y `AGENTS.md`; `commands/` nunca se instala. Se corrige la nota para reflejar que las skills nativas de `.agents/skills/` cubren el mismo flujo
- La plantilla de revision adversarial distingue correcciones menores (aplicar directo) de mayores (crear tarea nueva), pero el flujo mecanizado (`implementar-spec`) siempre ejecuta una unica pasada de correccion y descarta el trabajo como fallido si no queda aprobada, sin crear ninguna tarea nueva automaticamente. Se anade una nota que aclara este comportamiento real, dejando la distincion mayor/menor como guia solo para el flujo manual
- La seccion de reglas de Cursor instruia copiar `.cursor/` al proyecto sin advertir que la via de instalacion recomendada (`npx ... install`) no copia esa carpeta; se anade la misma nota de caveat ya usada para el backend Claude Code
- `CONTRIBUTING.md` pedia consultar `.claude-plugin/plugin.json` para reportar la version del framework en un bug report, pero ese archivo no se distribuye a los proyectos instalados via el CLI. Se reemplaza por `node bin/cli.js --version` o el marcador `<!-- sdd-framework: X.Y.Z -->` presente en `CLAUDE.md`/`GEMINI.md`/`AGENTS.md`, ambas vias accesibles desde una instalacion real
- El guard de pipeline SDD ascendia desde el archivo a escribir hasta la raiz del sistema de archivos buscando `ai_docs/tasks/`, sin detenerse en el directorio temporal del sistema. Un `ai_docs/tasks/` residual en ese directorio compartido (por ejemplo, de una ejecucion manual previa) se "prestaba" a cualquier archivo que se estuviera escribiendo dentro de el, provocando bloqueos en proyectos que no tienen ningun pipeline SDD que enforcar. El ascenso ahora se detiene en el directorio temporal del sistema
- `.gitignore` seguia sin llegar a los proyectos instalados via `npx github:...` pese al `.npmignore` con negacion explicita: ese flujo pasa por una extraccion intermedia de npm/pacote (distinta de `npm pack`) que renombra en caliente cualquier archivo llamado literalmente `.gitignore` a `.npmignore`, sin excepcion posible desde el propio repo (confirmado empiricamente y en el codigo fuente de `pacote`). Como ningun `.npmignore`/`.gitattributes` puede evitar ese renombrado, `.gitignore` ahora se distribuye desde `templates/.gitignore.template` (un nombre que esa logica no reconoce) y el CLI lo copia con el nombre correcto durante `install`/`update`; verificado contra el flujo real `npx github:...` con la cache de npx limpia
- El contador de acciones sin commit (presupuesto de turnos) perdia incrementos bajo llamadas concurrentes de subagentes, pudiendo dejar pasar de largo un tope de bloqueo configurado; la cuenta ya no pierde incrementos bajo esa concurrencia. Ademas, el contador ya no se reinicia solo porque otro comando mencione la frase "git commit" en su texto, y si reconoce un commit real precedido de una opcion global de git o entregado con el nombre de campo que usa el backend Antigravity
- El rastreador de lecturas (que alimenta el aviso "escribes sin haber leido") tambien perdia lecturas bajo llamadas concurrentes, lo que podia disparar el aviso sobre un archivo que si se habia leido; la escritura de su estado ya no pierde lecturas por esa concurrencia. Ademas, dos sesiones cuyos identificadores solo difieren en caracteres fuera del rango seguro dejan de compartir el mismo archivo de estado
- `compile.js --write` podia dejar las salidas generadas de una misma entrada con una mezcla de contenido nuevo y viejo si un fallo interrumpia la escritura a mitad; ahora una entrada aplica todas sus salidas o ninguna
- En el modo de implementacion concurrente, el commit de una task podia absorber en silencio el trabajo sin commitear de una task hermana en curso; el `add` y el `diff` que preparan el commit se acotan ahora a los archivos que la propia task declara
- Traducir un comando de Claude Code a skill de Codex/Antigravity corrompia en silencio cualquier ruta absoluta situada al inicio de una frase (por ejemplo `/tmp/salida.md`), confundiendola con una referencia a otro comando; la traduccion ahora solo reescribe referencias a comandos declarados en el manifiesto, y una ruta absoluta sobrevive intacta este donde este en el texto
- `install`/`update` aceptaban en silencio que una carpeta esperada del proyecto (`ai_docs/core`, `ai_docs/tasks`, `ai_docs/refs`) fuera en realidad un archivo existente, sin avisar ni fallar, dejando una instruccion de configuracion imposible de cumplir; y tres lecturas del archivo de contexto del backend (`CLAUDE.md`/`GEMINI.md`/`AGENTS.md`) morian con el error crudo del sistema de archivos en vez de nombrar el archivo y la causa, cuando ese archivo existia pero no era del tipo esperado (por ejemplo, un directorio). Los cuatro casos se detectan ahora y se reportan con su ruta y su causa
- **Una instalacion que fallaba a mitad de camino sobre un destino malformado (por ejemplo, con `ai_docs` ya creado como archivo en vez de directorio) dejaba en disco el archivo de bloqueo de instalacion.** Cualquier intento posterior sobre ese mismo destino, incluso despues de corregir la causa del primer fallo, se rechazaba por encontrar ese bloqueo: el destino quedaba permanentemente ininstalable. El bloqueo se retira ahora en toda via de salida, incluida una excepcion no prevista

### Security

- La vinculacion de una tarea a una spec aprobada usaba busqueda de subcadena sin limite de palabra: una tarea que solo mencionaba el descriptor de la spec como parte de otra palabra (por ejemplo "authentication" conteniendo "auth") quedaba vinculada por error, heredando la autorizacion de archivos de esa spec. Ahora la vinculacion exige el campo `Spec madre: <descriptor>` explicito en la task, en vez de inferirla de cualquier mencion en el texto
- El guard de commits solo detectaba `-n` aislado (seguido de espacio o fin de linea), asi que flags cortos combinados como `-na`/`-an` evadian por completo el bloqueo de `--no-verify`; verificado contra un repo real con un hook de pre-commit que siempre falla. Se amplia la deteccion para reconocer `-n` en cualquier posicion dentro de un grupo de flags cortos combinados
- La deteccion de llamadas de subagente en el hook de presupuesto de turnos solo comprobaba `agent_id` y `agent_type`, sin `is_sidechain`: una llamada que solo llevaba ese campo se trataba como hilo principal y, en modo bloqueante, se denegaba en vez de degradarse a aviso que el propio subagente pudiera atender
- Los hooks de presupuesto de turnos y de seguimiento de lectura escriben un archivo de estado por sesion en el directorio temporal del sistema sin ningun mecanismo de limpieza; en maquinas de larga duracion sin reinicios se acumulaban indefinidamente. Ambos hooks purgan ahora, de forma oportunista en cada escritura, los archivos de sesiones anteriores con mas de 24h de antiguedad, sin afectar nunca a la funcionalidad principal si el directorio temporal no es escribible
- El reconocimiento de invocaciones de `git` fallaba en las dos direcciones a la vez: `git -c <opcion> commit --no-verify` (una opcion global de git antes del subcomando, sintaxis corriente y no exotica) evadia por completo el bloqueo de `--no-verify`, mientras que un grupo de flags cortos validos que solo *contenia* una `n` (por ejemplo `-uno`, la forma corta de `--untracked-files=no`) se bloqueaba por error como si fuera `-n`. El reconocimiento ahora tokeniza el comando en vez de buscar subcadenas: distingue el subcomando y los flags reales del texto de un mensaje, y ya no confunde un flag que consume valor con `--no-verify`
- Un proyecto alojado bajo un directorio ancestro llamado literalmente `ai_docs` (el propio patron de instalacion de este framework dentro de un repositorio mayor) apagaba el guard de escrituras no planificadas entero, en los cuatro backends: cualquier archivo de codigo se leia como si fuera documentacion exenta. El guard ahora decide por la posicion del archivo relativa a la raiz del proyecto, no por si algun antepasado de la ruta absoluta se llama `ai_docs`
- El guard de escrituras no planificadas no reconocia `NotebookEdit`, la cuarta herramienta de escritura de Claude Code: codigo escrito en un cuaderno Jupyter evadia el gate por completo. El guard reconoce ahora esa herramienta y la ruta del cuaderno que edita
- En un parche que tocaba varios paquetes de un monorepo a la vez, el guard de escrituras del backend Codex resolvia el directorio de tasks una sola vez a partir del primer archivo del parche, y aplicaba ese mismo veredicto a todos los demas: el orden en que llegaban los archivos podia saltarse el bloqueo entero. Cada archivo se contrasta ahora con el plan que le corresponde por su propia posicion en el arbol, sin que el orden del parche cambie el resultado
- **Limite conocido: el reconocimiento de invocaciones de `git` no cubre un envoltorio con argumentos propios** (`timeout 30`, `nice -n 10`, `xargs`, entre otros), **ni una palabra suelta en cabeza de segmento** (un nombre de rama de `case`, o el nombre de una funcion de shell definida antes del commit). Un comando de este tipo delante de `git commit --no-verify` no se detecta hoy. Cerrar cualquiera de los dos exige una decision de diseno propia, no ampliar los conjuntos ya reconocidos
- **El bloqueo de commits sin revisar volvia a evadirse en varias formas de sintaxis de shell:** un comando de commit precedido de `sudo`/`doas`, metido dentro de una agrupacion (`{ }`, `( )`, `if`/`then`, un bucle), encadenado tras un `&` suelto, o con una asignacion de variable de entorno colocada despues de un envoltorio (por ejemplo `sudo FOO=bar git commit --no-verify`). Las cuatro formas se bloquean ahora igual que la invocacion directa

### Breaking

- **La vinculacion de una task a su spec exige ahora el campo `Spec madre:` explicito.** Antes bastaba con mencionar el descriptor de la spec en cualquier parte del texto de la task para heredar la autorizacion de escritura de esa spec; una mencion en prosa deja de vincular. Si una task existente no declara `Spec madre: <descriptor>` en su cabecera, la escritura de sus archivos declarados pasa a denegarse hasta que lo haga. Al actualizar: revisa las tasks abiertas de tu proyecto y anade el campo donde falte — la plantilla de tasks del framework ya lo declara desde su origen
- **Se retira la regla documentada «auditoria cruzada obligatoria con 3 o mas tasks».** Nunca reflejo el comportamiento real: el flujo de planificacion audita la spec completa en cada pasada, sin importar cuantas tasks tenga. Si tu proceso citaba esa regla para decidir cuando auditar a mano, no hay ninguna accion que tomar — la auditoria automatica ya cubria ese caso; el umbral se retira de la documentacion porque nunca fue cierto

- **`sdd-commit-guard.js` no impedia saltarse sus propias reglas.** Solo advertia sobre subjects largos o mensajes vacios, pero no detectaba `--no-verify`/`-n` en `git commit` o `git push`. Ahora bloquea ambos, reutilizando la logica ya existente en `sdd-commit-rules.js`

### Security

- **Limite honesto de la senal de revision documentado.** La senal (un hash del diff cacheado) protege contra commits sin revisar por accidente, pero no puede endurecerse contra un falsificador deliberado con acceso a shell sin trasladar la misma superficie de ataque (sistema de archivos o variables de entorno) a un secreto compartido igual de accesible. Se documenta la limitacion en el README, justo despues del parrafo de `SDD_GUARD_SKIP=1`, y en el docstring del modulo del hook; la recomendacion para una frontera realmente dura sigue siendo proteccion de rama + CI

### Aprendizajes de esta ronda

- El canario de vocabulario que detecta residuos de un modelo retirado debe escanear tambien codigo fuente y skills por backend, no solo los documentos de contexto en la raiz: un residuo sobrevivio sin deteccion hasta que se amplio su cobertura.
- Los campos muertos de un schema (como `independiente`) son residuos silenciosos: ningun test los detecta hasta que se buscan explicitamente, aunque ya no describan ningun comportamiento real.
- La proteccion de archivos editados a mano en `update` (config, `CLAUDE.md`/`GEMINI.md`/`AGENTS.md`) extiende un patron de "no pisar lo que el usuario ya toco" que el propio CLI aplicaba a `ai_docs/core/` y `ai_docs/tasks/`; conviene generalizarlo, no reinventarlo por archivo.

### Breaking

- **`scripts/update-framework.sh` eliminado, reemplazado por el CLI.** Usa `npx github:gmoncor/agentic-engineering-framework update --backend <backend>` en su lugar. Si lo habias copiado a tu proyecto, tu copia local sigue funcionando pero ya no se actualiza junto con el framework
- **El gate de revision pasa de advisory a bloqueante.** Con `sdd_review_gate.enabled: true`, un `git commit`/`merge` cuyo diff no conste revisado ahora se deniega (antes solo avisaba). La via para satisfacerlo es pasar la revision adversarial por task; el escape puntual sigue siendo `SDD_GUARD_SKIP=1`
